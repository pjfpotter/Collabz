What Collabz Does

You tap "Matches". Here is everything that happens before the page appears.

A matchmaker for bootcamp students

Collabz pairs software students with business students by chemistry, not by CVs. Everybody picks tags from fixed lists, the app scores every pair, and the best fits get to talk.

1
Scan a QR code and sign up

No password. A magic link arrives in your inbox.

2
Pick tags, never type

Hero story, energy, qualities, what you are seeking. The app builds your alias, like "The Calm Captain".

3
See your top 5 and one surprise

A chemistry score ranks everyone. A random "glitch match" is added on purpose.

4
Both say yes, then talk

A connection request must be approved before a private conversation opens.

03

The Chemistry Formula

One small function turns "two people" into a number. Learn to read it, then you can question it.

A recipe with three ingredients

Think of a cocktail recipe: one ingredient is the base, two are only a splash. The score is one big ingredient plus two small ones.

🧩

Complement × 3

One point for each thing you are seeking that the other person can offer, counted both ways. The main signal, hence ×3.

🎶

Overlap

+1 for the same Energy, +1 for the same Vibe Diagnosis. A rapport bonus.

⚡

Tension

+1 when your Hero Stories differ. A spark bonus.

ℹ️
What is NOT in the formula

Skills, interests and course never change a score. A test pins this, so no AI edit can quietly change it.

Worked example: Sam and Priya

1
Sam seeks a Builder, and Priya is one

Complement: 1

2
Priya seeks a Storyteller, and Sam is one

Complement: 2, so 2 × 3 = 6

3
Both picked the "Sea Captain" energy

Overlap: +1

4
Their Hero Stories are different

Tension: +1

Total: 6 + 1 + 1 = 8. Swap Sam and Priya and you still get 8, because the formula looks in both directions.

The real function

This is the whole of calculateScore from src/lib/matching/score.ts. Notice there is no database in it.

CODE 
export function calculateScore(a: PersonTags, b: PersonTags, pairings: Pairing[]): ScoreResult {
  const complement =
    findSatisfiedSeekingTags(a, b, pairings).length +
    findSatisfiedSeekingTags(b, a, pairings).length;

  const sharedEnergy = findSharedTagIds(a.energy, b.energy).length > 0 ? 1 : 0;
  const sharedVibe = findSharedTagIds(a.vibeDiagnosis, b.vibeDiagnosis).length > 0 ? 1 : 0;
  const overlap = sharedEnergy + sharedVibe;

  const tension = heroStoriesDiffer(a, b) ? 1 : 0;

  return {
    score: complement * COMPLEMENT_WEIGHT + overlap + tension,
    complement,
    overlap,
    tension,
  };
}
PLAIN ENGLISH

Take two people's tags and the pairing list, and hand back a score.

Count A's wishes that B can answer, then B's wishes that A can answer, and add them. That is the complement.

Did they share an Energy? That is 1 or 0. Same question for Vibe Diagnosis.

Add the two answers together. That is the overlap.

Do their Hero Stories differ? 1 or 0. That is the tension.

Give back the total (the complement is worth 3 each), and also the three parts, so "why you match" can explain itself without recalculating.

💡
Pure functions are easy to trust

A pure function can be tested with a few lines and a hand-worked example. When you ask AI for logic, ask for it "as a pure function with no database".

Two checks, in this order on purpose

These are the first two checks, copied from src/lib/messages/sendMessage.ts.

CODE 
  if (
    !conversation ||
    (conversation.userAId !== senderId && conversation.userBId !== senderId)
  ) {
    return refuse("not-found");
  }

  // Check 2.
  if (conversation.closedAt !== null) {

PLAIN ENGLISH

If there is no such conversation, or you are neither of its two people...

...say "not found". A made-up id and somebody else's id get exactly the same answer.

Only after you are proven to be one of the two people do we tell you it is closed.

That order means a stranger learns nothing, not even whether the conversation is closed.

⚠️
Order of checks is a design decision

If "closed" were checked first, a stranger could tell a real conversation from a fake one by the different answer. When AI rewrites validation, ask it to keep the order and say why.

05

Safe by Default

How Collabz is built so that forgetting something leaves it locked, not open.

Doors that lock themselves

A fire door is designed to shut unless something holds it open. Collabz's riskiest tool, the "sign in as any pretend student" switcher, works the same way: off unless deliberately held on.

CODE 
export function isPretendCohortEnabled(): boolean {
  const switchedOn = process.env.PRETEND_COHORT === "on";
  const isProductionDeployment = process.env.VERCEL_ENV === "production";

  return switchedOn && !isProductionDeployment;
}
PLAIN ENGLISH

One yes/no question: is the pretend cohort allowed here?

First lock: someone must have set a setting to exactly "on". Forget to set it and the answer is no.

Second lock: are we on the real, live site? Vercel tells us.

Both must be true: switched on and not production. Even a mistaken setting on production stays refused.

💡
Fail closed

Engineers call "off unless switched on" fail closed or opt-in. Whenever AI adds a flag that unlocks something risky, ask: "what happens if this variable is missing?" The answer should be "locked".

Who is using the app right now?

Every page asks getCurrentUser(). It gathers facts, then one small function decides.

CODE 
  const { sessionUser, pretendUser } = people;

  if (sessionUser) {
    const isSuspended = sessionUser.suspendedAt !== null;
    if (isAccountFinished(sessionUser) && !isSuspended) {
      return sessionUser;
    }
    return null;
  }

  return pretendUser;
PLAIN ENGLISH

Two candidates arrive: the person from a real sign-in, and the dev switcher's pretend person.

If there is a real sign-in, it wins. Always.

A real person is accepted only if they finished sign-up and are not suspended.

Otherwise nobody. The switcher is NOT used as a fallback, so a real person is never silently swapped for a pretend one.

With no real sign-in, the pretend user (if the switcher is on here) is returned.

This function takes plain objects, so each case has a one-line test. Every page in the app depends on it, which is why the team kept it small and tested.

💡
Small, reviewable steps beat big leaps

AI is most reliable on a task small enough to check. "Do one task group, then stop" is not slowness; it is how you catch a wrong turn while it is cheap.

Lanes, shared helpers, and the rule to not cross

🛣️

Your own slice

Each person owns specific routes. Change only those.

🤝

Shared helpers

Reach another track only through getCurrentUser, scoreUser, openConversation and friends. Never their internals.

🚧

Flag schema changes

Every track builds on the same tables, so a change to schema.prisma is raised with the group first.

🎭

Pretend cohort

32 pretend students on the dev database, so nobody waits for another track.

This is also how two AI agents working at once avoid conflicts: each stays in its lane, and the shared helper keeps its name and return value even when its inside changes.

Reading a symptom

The API route answers with a number. The number tells you which layer to inspect. This is the real table from src/app/api/messages/[conversationId]/route.ts.

CODE 
const STATUS_FOR_REFUSAL: Record<SendRefusalReason, number> = {
  "not-found": 404,
  closed: 409,
  "not-connected": 409,
  empty: 422,
  "too-long": 422,
};
PLAIN ENGLISH

A lookup table: for each reason the helper can give, which number to send back.

Not yours or does not exist: 404.

Closed, or the two are no longer connected: 409, a conflict with the current state.

Empty or too long: 422, the words themselves are not acceptable.

"It's not showing up": where to look

1
Is it a page or an action? Check the status number

401 means not signed in, 404 not yours or missing, 409 state conflict, 422 bad input.

2
Is the person even visible?

Unfinished profiles and suspended people vanish from the graph, search and scores by design.

3
Did a pairing or tag change without a rescore?

Pairing edits change no score until "Rescore everyone" is pressed.

4
Which database are you on?

Laptops, previews and tests use the dev branch. Only the live site uses production.
