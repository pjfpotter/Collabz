The folders tell the same story

You can read the architecture from the folder names alone. This is why the team keeps functions small and well named.

src/app/Pages. One folder per address: /matches, /graph, /messages.
api/Addresses that return data, not pages. For example sending a message.
admin/Pages only admins can open.
src/components/Reusable pieces: NavBar, TagChip, PersonCard.
src/lib/The rules. Plain functions with no screen in them.
matching/Scores, top 5, glitch match.
requests/Sending and answering connection requests.
messages/Sending and reading messages.
admin/, safety/, account/One folder per capability.
prisma/The schema, the seed data and the pretend cohort.
openspec/The written specs and every change proposal. The source of truth.
💡
Separation of concerns

Pages draw, lib decides, the database remembers. Engineers call this separation of concerns. When you ask AI for a new rule, say "in lib", not "in the page".

The filing cabinet, one drawer

This is the real GlitchMatch table from prisma/schema.prisma. Each person gets exactly one random surprise match.

CODE 
model GlitchMatch {
  userId        String @id
  user          User   @relation("GlitchMatchOwner", fields: [userId], references: [id])
  matchedUserId String
  matchedUser   User   @relation("GlitchMatchTarget", fields: [matchedUserId], references: [id])

  @@index([matchedUserId])
}
PLAIN ENGLISH

A table called GlitchMatch. Each row is one person's surprise.

The owner's id is the row's id. So one person can only have one row: "one glitch match each" is enforced by the database itself.

A link from that id to the real person in the User table.

The id of the person they were matched with, and a link to that person too.

Make it quick to look up "who is somebody else's surprise".
